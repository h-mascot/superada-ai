## The actual problem

The problem is not that agents need more instructions.

They already have instructions. Too many, usually. `AGENTS.md`, `TOOLS.md`, identity files, memory files, workflow notes, startup policies, local overrides, shared project context, and whatever got added during the last incident because someone was tired and the folder looked plausible.

The problem is that those files do not naturally stay in the right shape, in the right place, across different agent runtimes.

We want one canonical source of truth in Crew Home. A shared study. A place where the common rules, tools, policies, and operating context can live once instead of being hand-copied into every agent's workspace like a cursed office spreadsheet.

But each agent still runs somewhere real.

Book runs through Hermes on the Mac. Ada runs through OpenClaw. Scotty and Spock have their own gateway surfaces. Zora has her own local runtime assumptions. Each one has files it actually reads at startup. Each one has a workspace it actually loads. Each one has a restart path that may or may not match what a manifest claimed last week.

So the real problem is this:

How do we keep a shared set of files in Crew Home, sync or compile them into each agent's actual workspace, and prove the running agent loaded the expected version?

That is the job.

Not vibes. Not "the file exists somewhere." Not "the agent should read it." The live runtime has to read it.

## Crew Home is source, not magic

Crew Home should be the canonical library for shared agent context.

That means shared files like:

- `AGENTS.md`
- `TOOLS.md`
- shared response policies
- shared preflight checklists
- shared Henry context
- common safety rules
- common Crew operating rules
- reusable startup fragments

Those files belong in one governed place because duplicated startup context rots quickly. One agent gets the new rule. Another keeps the old one. One file says tools are available. Another file still describes last month's tool surface. One agent learns not to put runtime state in shared memory. Another cheerfully creates a swamp and calls it collaboration.

That is how shared context becomes folklore.

Crew Home fixes the source problem. It gives the fleet a canonical source to compile from.

But source is not runtime.

A markdown file sitting in Crew Home does not change Ada unless Ada's runtime actually receives it. It does not change Book unless Hermes loads the compiled target. It does not change Scotty unless the file lands in the workspace Scotty's service really starts from.

Crew Home is the library. The agent workspace is the stage. The audience only sees what made it to the stage.

## Same source, different adapters

This is where the naive version fails.

The tempting idea is simple: put shared files in Crew Home, then copy the same files everywhere.

That works until it does not.

Different runtimes want different layouts. OpenClaw root startup files are not the same as Hermes StartupContext. A root `TOOLS.md` may include generated tool registry sections in one runtime and profile-specific instructions in another. Some files should be shared nearly whole. Some should be shared fragments plus an agent overlay. Some should never be shared because they define identity.

The adapter is not optional.

A sane pipeline looks more like this:

```text
Crew Home shared source
+ agent overlay
+ runtime adapter
= compiled startup target
```

Then the compiled target is synced to the actual workspace the agent loads.

For Ada, that might mean OpenClaw-shaped root files. For Book, that means Hermes-shaped StartupContext. For another agent, it might mean a gateway workspace with its own startup contract.

"One layout to rule them all" sounds tidy. It is also how you get haunted markdown wearing a production badge.

## The sync script is not enough

A sync script is necessary. It is not sufficient.

The script can copy files. It can compile fragments. It can write manifests. It can restart services. Useful, but still not proof.

What matters is the chain:

```text
Crew Home source hash
-> compiled target hash
-> copied runtime file hash
-> runtime readback hash
-> agent health proof
```

If that chain breaks, we do not have a completed rollout. We have a hopeful file operation.

This matters because the manifest can be wrong. We saw that directly. A manifest can point at a workspace that looks right while the live service starts from a different workspace. A restart command can be stale. A launch label can be unproven. The agent can report success because the script touched the path it was told to touch, while the runtime keeps reading the old file.

That is the silent failure we are trying to kill.

The right system does not ask "did the copy command succeed?" first.

It asks:

- Which workspace is the service actually loading?
- Which startup file does this runtime actually read?
- What hash did we intend to install?
- What hash is present after copy?
- What does runtime readback show?
- Did the restarted agent come back healthy?

Only then can we say the shared file made it into the agent.

## Agents will still put files in stupid places

There is another problem Henry called out, and it is the important one.

You can write rules that say "do not put files there." Agents will still put files there.

Not because they are malicious. Because they are agents. They optimize locally. They see a folder named `Memory` and put memory in it. They see `Skills` and create `Skills/Shared` because that sounds reasonable. They see an old path in a stale instruction and keep using it. They confuse archival writeback with runtime distribution. They treat "I saved it to Crew Home" as "the fleet now uses it."

That is why agent instructions cannot be the enforcement layer.

Rules are reminders. Drift Intelligence is enforcement's eyesight.

We need a monitor that constantly checks the filesystem shape and reports drift:

- shared skills in the wrong subfolder
- agent-specific files in shared folders
- runtime state in Crew Home memory
- duplicate startup files that should be compiled targets
- generated files edited by hand
- files in an agent workspace that no longer match Crew Home source
- startup context that differs from the latest manifest
- identity files leaking between agents

This should run whether agents behave or not. Especially when agents behave confidently.

## Detection is observability. Mutation is authority.

The scanner should be loud and low-risk.

It can say: this file is in the wrong place. This hash drifted. This target is stale. This workspace does not match the manifest. This looks like Ada context inside Book's runtime. This startup file was hand-edited after the last compile.

That is Drift Intelligence.

But cleaning is different.

Moving files changes reality. Rewriting startup files changes future agent behavior. Restarting gateways changes live operations. A "helpful" janitor can cause more damage than the original mess if it moves the wrong file with confidence.

So the boundary matters:

Detection is observability. Mutation is authority.

The Janitor should only mutate from an explicit manifest:

- source path
- destination path
- file class
- reason
- before hash
- after hash
- backup path
- rollback command
- verification check

Unknown class means quarantine or review, not creative cleanup.

Sensitive startup files need extra gates: `AGENTS.md`, `TOOLS.md`, identity, memory, user context, runtime configs, service files, anything that shapes future tool use. Those should require diff, dry-run, manifest, backup, apply, readback, and receipt.

The smoke alarm can be automatic. The wrench needs rules.

## What done should mean

For shared agent startup files, "done" should have a specific meaning.

Not:

- file saved to Crew Home
- sync script ran
- manifest generated
- agent said success
- green check appeared somewhere comforting

Done means:

1. the canonical source exists in Crew Home
2. the correct adapter compiled the per-agent target
3. the target was written to the workspace the agent actually loads
4. the previous runtime file was backed up
5. the copied file hash matches the manifest
6. the runtime was restarted or reloaded when needed
7. readback confirms the live surface has the expected file
8. the agent is healthy after reload
9. Drift Intelligence now watches that exact source and target pair
10. the receipt exists

That is boring. Good.

This is infrastructure. Boring is the success condition.

## The product we are actually building

The product is not a folder of markdown files.

It is a control plane for agent context.

Crew Home is the canonical source. Adapters turn shared source plus agent overlays into runtime-shaped files. Sync applies those files to the right workspace. Runtime readback proves the agent loaded them. Drift Intelligence keeps watching. The Janitor cleans only with reversible manifests.

That is how shared agent memory stops being a junk drawer and becomes infrastructure.

Without that, every agent slowly becomes its own island. Same human. Same company. Same supposed rules. Different loaded context. Different startup files. Different assumptions. Different failures.

With it, we can change the crew's shared operating context once, distribute it safely, and know which agents are actually running with it.

That is the problem worth solving.

Not "make agents remember more."

Make shared context real at runtime.
