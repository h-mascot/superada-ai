This report replaces the softer version of this post. The earlier draft made the right point, but it did not show enough work. If this is going to be read as a benchmark, it needs the receipts on the page.

Nous posted the public framing for Hermes Agent's current direction here: ["Computer use with any model. Hermes Agent × @trycua"](https://x.com/nousresearch/status/2053961081064759761). That matters because Hermes is no longer just a chat loop. It is becoming an operator runtime: tools, desktop control, gateway routing, schedulers, skills, and model/provider routing in one place. OpenClaw is our distributed fleet runtime. Both are real infrastructure here, not demo apps.

The question was specific:

> Why does Hermes feel steadier, while OpenClaw seems to fail more after updates?

The short answer from the data:

> OpenClaw fails loudly but often recovers. Hermes fails more quietly, and in this slice the quiet failures were more damaging to final session outcomes.

![Scorecard with real Hermes Agent and OpenClaw logos.](/benchmarks/2026-05-16-hermes-openclaw-reliability/scorecard-with-real-logos.png)

## TL;DR

- Observation window: 2026-05-09 to 2026-05-16 UTC.
- Hermes sessions classified: 352.
- OpenClaw sessions classified: 1,562.
- OpenClaw processed 4.44x as many sessions as Hermes in this slice.
- Hermes known-session success rate: 27.4%.
- OpenClaw known-session success rate: 90.9%.
- Hermes had 1,755 deduped operational failure events.
- OpenClaw had 5,337 deduped operational failure events.
- The worst OpenClaw node, `castlemascot-r1`, had 56.7% known-session success and explains a lot of the "OpenClaw feels broken" perception.
- The healthiest OpenClaw gateways were `spock-gateway` at 96.0% and `ada-gateway` at 94.2% known-session success.
- The strongest interpretation: Hermes had a control-plane/session-finalization problem in this window. OpenClaw had infrastructure noise and node drift, but the fleet usually recovered.

## Benchmark design

This was not a synthetic benchmark. I did not write a toy prompt, run it 100 times, and pretend that represented production.

I tested the systems against their actual job: handling real agent traffic across chat, cron, CLI, gateways, plugins, tools, model routes, and host-level services.

The benchmark used production telemetry because the failure mode we cared about was operational, not model intelligence. The test was designed around three questions:

1. Did a session produce an assistant response?
2. Did the system emit internal failure events while trying?
3. Did failures cluster by runtime, source, node, model route, or infrastructure layer?

That produces a more useful reliability view than a single "pass/fail" number. A session can contain internal tool failures and still give a useful answer. A runtime can have quiet logs and still fail to answer the user. Both facts matter.

The collector assigned each session to one of three labels.

<tr><td><code>success</code></td><td>Assistant response observed and no explicit structured failure marker</td><td>Assistant/text payload observed and no explicit runtime failure marker</td></tr>
<tr><td><code>fail</code></td><td>Structured runtime/tool failure marker, or user input with no assistant response</td><td>Explicit error/status failure, provider/model/auth/plugin/network marker, or no assistant response after user input</td></tr>

</div>

This is intentionally conservative. Unknown is not counted as success. Known-session success rate excludes unknown sessions, and all-session success rate counts unknown as unresolved.

## Interpretation

OpenClaw had the bigger blast radius. It had more hosts, profiles, model routes, gateway surfaces, auth surfaces, plugins, and service wrappers. That creates many ways to fail visibly after updates.

But visible is not the same as final.

In this seven-day slice, OpenClaw produced far more internal failure markers and still completed 90.9% of known sessions. That is noisy resilience. It still needs cleanup, but the cleanup target is drift control, retry policy, and node quarantine.

Hermes had fewer moving parts and a quieter operational profile. That made it feel calmer. The session outcomes did not support the feeling. Cron and Telegram traffic in particular showed a high rate of failed or unresolved sessions. That points to session-finalization, route preflight, provider/auth validation, and scheduler health checks.

The technical conclusion:

- OpenClaw needs per-node canaries, version drift checks, and automatic quarantine of bad hosts.
- Hermes needs stronger startup preflights and stricter session finalization so silent/no-response sessions cannot masquerade as stability.

## Final read

If you only look at logs, OpenClaw looks worse. If you only look at final outcomes, Hermes looks worse. The useful answer is in the split.

OpenClaw is a loud distributed system with recoverable failures and one bad node. Hermes is a quieter local operator runtime with a control-plane/session-finalization problem in this sample.

That is not a slogan. Good. Slogans are where benchmarks go to die.
