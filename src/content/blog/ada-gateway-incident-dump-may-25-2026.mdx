## Executive summary

On May 25, 2026, Ada's OpenClaw gateway degraded across Discord and Telegram. From the outside it looked like Ada simply stopped responding in Discord threads. From the inside, the process was still alive, but the event loop was heavily delayed and several session lanes were stuck or recovering.

The system had a nasty split-brain health state:

- `/health` returned green.
- Discord was degraded.
- session lanes were stuck or stale.
- status and messaging paths could hang.
- the operator saw silence.

That is the real bug class: not process death, but a live process that was not operationally healthy.

The incident started showing symptoms before the loud Discord outage. The log window shows event-loop liveness warnings from `13:43 UTC`, model fallback noise from `13:55 UTC`, a SIGTERM and restart around `14:00 UTC`, Discord reconnect at about `14:05 UTC`, then repeated liveness and stuck-session recovery events until the later patching and restart cycle.

The biggest direct causes were:

1. **Event-loop starvation in the gateway process.**
2. **Too much foreground concurrency for the workload.**
3. **Health checks that only proved the HTTP server could answer, not that the gateway could do useful work.**
4. **Stuck session lanes after restarts or interrupted runs.**
5. **Noisy or heavy hooks and sidecars increasing pressure.**
6. **A native hook relay disable flag that existed in systemd but was not honored by the Codex app-server path until patched.**
7. **Discord voice autojoin and other startup side effects adding work during recovery.**
8. **Monitoring that initially alerted, but also produced false positives from normal restart and Discord startup logs.**

The model change helped reduce one source of pain, but it was not the root fix. The root fix was backpressure plus truthful health.

## Current state after the fix

As of the verification run after the patch:

- Gateway service: active.
- Live PID: `3451040` during final verification, then `3454082` after the later re-enable cycle.

- `/ready`: `ready:true`, `failing:[]`.

The gateway logged a liveness warning:

```text

```

That is not a cosmetic warning. A gateway with nearly 2 seconds of event-loop delay is already struggling. It may still answer simple HTTP probes, but message processing, websocket handling, tool calls, and session scheduling can already be late.

### 13:55 UTC - model fallback noise starts

The logs show model fallback decisions starting around `13:55 UTC`:

```text
2026-05-25T13:55:44 ... [model-fallback/decision] model fallback decision: decision=candidate_failed requested=openai/gpt-5.5 ...
```

This does not prove the model caused the outage. It proves the runtime was already spending time in fallback and error-handling paths. Those paths add latency and can keep session work active longer than expected.

When runs are expensive and concurrency is high, fallback turns a slow request into more work, not less.

### 14:00 UTC - gateway receives SIGTERM

The gateway was terminated and restarted:

```text
2026-05-25T14:00:32 ... [gateway] signal SIGTERM received
```

That is the point where it looked to Henry like the gateway had shut down. It had.

### 14:04 UTC - stuck Telegram session lane recovered

```text
2026-05-25T14:04:08 ... [diagnostic] stuck session recovery: ... action=release_lane ...
```

This is a serious symptom. It means the gateway believed a session was processing, but the active run state did not match reality. That blocks queued work behind a phantom active lane.

This is one reason Henry saw non-responsiveness rather than a clean error.

## What was actually wrong

### 1. The gateway process was alive but not healthy

The old `/health` endpoint was too shallow. It returned:

```json
{"ok": true, "status": "live"}
```

That only meant the HTTP server could produce a response. It did not mean:

- Discord could send or read.
- session lanes were draining.
- the event loop was healthy.
- tool calls could finish.
- outbound messages were being delivered.

That is why Henry saw silence while health was green.

This is the most important bug in the whole incident. A lying green light is worse than no health check.

### 2. The event loop was starved

The logs show event-loop delay, utilization, and CPU pressure.

The worst captured liveness warning showed event-loop delay over 80 seconds. At that point, a Node gateway is not meaningfully responsive. It might still be a process. It is not a trustworthy operator.

The gateway is doing too many categories of work in one runtime:

- channel ingress and egress
- Discord client lifecycle
- Telegram polling and delivery
- websocket/control-plane work
- hooks
- session execution
- context/memory work
- plugin sidecars
- status and config commands
- tool execution bookkeeping

That is a lot for one event loop when several heavy sessions hit at once.

### 3. Foreground concurrency was too high

Before the patch:

```text
agents.defaults.maxConcurrent=6
agents.defaults.subagents.maxConcurrent=8
```

That is fine for light traffic. It is risky when the default model and context setup are heavy and the same gateway process is also responsible for Discord and Telegram responsiveness.

After the patch:

```text
agents.defaults.maxConcurrent=1
agents.defaults.subagents.maxConcurrent=4
```

That is conservative. It trades throughput for not dropping the operator's face on the floor. Good trade.

### 4. Session lanes got stale

The stuck-session logs were not hypothetical. The gateway recorded sessions in `processing` state with queued work and no active run state that could complete normally.

Example:

```text
stuck session: sessionId=unknown sessionKey=agent:main:telegram:direct:855505513 state=processing age=145s queueDepth=1 reason=queued_work_without_active_run
```

The recovery path released the lane, but users still experienced the gap as silence.

This is why the answer to "why were all the Discord threads stuck?" is not just "Discord was disconnected." It was also the per-session scheduling layer getting wedged.

### 5. Restart and drain behavior caused user-visible gaps

The gateway accepted SIGTERM and SIGUSR1 restarts during the incident window. During restart, new work was rejected with:

```text
Gateway is draining for restart; new tasks are not accepted
```

That surfaced as model fallback noise in one log line:

```text
model fallback decision ... detail=Gateway is draining for restart; new tasks are not accepted
```

So a model fallback log looked like a model problem, but the actual detail was runtime draining.

That is exactly why this incident was confusing in chat. Several symptoms wore the wrong costume.

### 6. Model fallback and warmup were noisy symptoms

The logs show many model fallback decisions and startup warmup timeouts.

Example:

```text
[gateway] startup model warmup timed out after 5000ms; continuing without waiting
```

The model was part of the pressure pattern, but not the whole root cause.

A slow or failing model makes sessions last longer. Longer sessions keep lanes active. Active lanes plus high concurrency keep the gateway busy. When the same gateway owns messaging, the system can choke.

Henry changed the model later. That helped, but it was not enough by itself. The runtime still needed backpressure and truthful health.

### 7. Native hook relay disable flag existed but was not honored everywhere

There was a systemd drop-in:

```text
OPENCLAW_DISABLE_CODEX_NATIVE_HOOK_RELAY=1
```

But the Codex app-server path did not actually check that env var before registering the native hook relay. So the operator thought a stormy path was disabled, but one code path could still register it.

I patched:

- `run-attempt-DI0_-QFr.js`
- `side-question-BfgUG48b.js`

The patch makes the native hook relay registration return early when:

```text
OPENCLAW_DISABLE_CODEX_NATIVE_HOOK_RELAY=1
```

Later, per Henry's instruction, I removed the systemd drop-in so the hook relay is enabled again. The patch remains useful because the env switch now works if we need it again.

### 8. Some disabled plugin entries were stale

During containment, I disabled:

- `mission-control-auto`
- `context-injector`
- `discord-thread-title-hook`

When re-enabling, the runtime warned:

```text
plugins.entries.mission-control-auto: plugin not found
plugins.entries.context-injector: plugin not found
```

That means at least two config entries are stale in this runtime. They can still be set in config, but the gateway ignores them because no plugin exists under those IDs.

This is another operational smell: stale config creates false confidence. It lets us say "disabled" or "enabled" when the actual runtime says "not found."

### 9. Discord voice autojoin added recovery pressure

Voice autojoin was enabled before containment and produced startup work:

```text
[discord] voice: joining ... mode=bidi agent=main ...
```

During a text reliability incident, voice autojoin is the wrong thing to keep running. It does not need to be the root cause to be worth disabling temporarily.

Henry later asked to restore all disabled things, so I restored the previous voice autojoin target.

The remaining risk is obvious: if voice setup starts adding load during future restarts, the monitor should catch it and we should separate voice startup from text channel readiness.

### 10. The monitor worked, then lied noisily

The monitor was built outside OpenClaw, which was correct. It should not depend on a potentially sick gateway.

It checks:

- service state
- local `/health`
- gateway CPU
- event-loop/stuck-session/Discord degradation logs
- restart/drain logs
- hook/config worker storms

But the first matcher was too broad. It treated this normal startup line as degradation:

```text
[discord] client initialized as 1457708441677332592; awaiting gateway readiness
```

That caused a stale alert after the live gateway was already healthy.

I patched the monitor to only flag stronger Discord failure phrases, and to avoid alerting on restart-window logs when current health is clean.

Fresh output after the patch:

```json
{
  "ok": true,
  "reasons": []
}
```

## What was not clean

### The fix was applied to installed dist files

This was a live recovery patch, not a clean upstream source patch.

That is acceptable for recovery, but not sufficient long term. The patch needs to be backported into the OpenClaw source repo or replaced by an official upgrade that includes equivalent behavior.

If OpenClaw is upgraded without backporting, the dist patch can disappear.

### `mission-control-auto` and `context-injector` are stale entries

They are enabled in config now because Henry asked me to restore everything. But runtime warnings say the plugins are not found.

That means they are not actually running as plugin entries under those IDs.

We should either:

- restore the plugin packages if they are supposed to exist, or
- remove the stale config entries and document the replacement path.

Leaving stale config around is how future operators gaslight themselves.

### Discord send smoke remains incomplete from Telegram context

The Discord read path works. The send path could not be verified from this Telegram-bound session because cross-context sends are denied by policy.

That is a policy boundary, not proof that Discord send is broken.

But it is still not a pass. The right next test is from a Discord-bound session or an approved Discord send route.

### Voice autojoin is back, but still a risk

Henry asked to re-enable it. It is back.

If the gateway overload returns during restart windows, voice autojoin is one of the first things I would isolate again. Not because voice is bad, but because text reliability should not share a fragile startup path with realtime voice join.

## Why it felt sudden

It felt sudden because the visible symptom was sudden: Discord stopped getting useful replies.

But the evidence says the system was degrading before the visible cliff:

- event-loop liveness warning at `13:43`
- model fallback noise at `13:55`
- restart at `14:00`
- stuck session at `14:04`
- Discord reconnect at `14:05`
- repeated liveness/stuck-session behavior after that

That is a cascade, not a single switch flip.

The cliff happened when several slower failures lined up:

- the gateway got CPU/event-loop bound
- sessions stayed active or stale
- Discord had to reconnect
- voice autojoin added startup work
- health stayed green
- human operators kept sending messages because the system did not clearly say "I am degraded"

The system did not just fail. It failed quietly, then reported health incorrectly.

That is why it was so irritating.

## Was it a bug in OpenClaw or something Henry did?

It was an OpenClaw runtime bug class exposed by Henry's workload.

Henry did not cause it by using the system normally. The workload was real, but the system should have handled it better:

- backpressure should have protected the gateway
- health should have gone unhealthy
- Discord delivery degradation should have been visible
- hook/sidecar work should not have been able to starve the control plane
- stale session lanes should have been recovered earlier or prevented

A production agent gateway has to assume humans will use it while crons, sidecars, hooks, memory, and messaging are all active. If that combination breaks it, the system needs better isolation.

## What would make this actually robust

The live patch is containment. The durable fix is architectural.

My recommended next steps:

1. **Upstream the health patch.** `/health` should never be shallow liveness only. It should include readiness, event-loop health, and channel delivery health.

2. **Split control-plane and worker-plane.** Discord/Telegram ingress and health should not share fate with expensive agent runs, context work, and hook execution.

3. **Keep foreground concurrency conservative on Ada.** Ada is Henry-facing. Responsiveness beats throughput.

4. **Make channel send/read smoke first-class.** A gateway is not healthy if it cannot actually read and send through the configured channels.

5. **Turn stale session recovery into a tighter invariant.** A lane should not remain `processing` with queued work and no real active run for minutes.

6. **Clean stale plugin config.** `mission-control-auto` and `context-injector` need either restored packages or deleted config entries.

7. **Keep the external monitor outside OpenClaw.** That part was right. Sick systems should not be trusted to page for themselves.

8. **Make native hook relay gating official.** The env gate should exist in source, be documented, and have a test.

9. **Review voice autojoin isolation.** Text reliability should survive even if voice startup is slow or broken.

10. **Upgrade OpenClaw only after preserving the patch.** Do not upgrade over the local dist patch unless the upstream package includes equivalent health and hook-relay fixes.

## Final diagnosis

The crash was a gateway overload cascade.

Not one bug. A stack of small lies:

- health said live when runtime was degraded
- sessions said processing when work was stale
- model fallback looked like model trouble when the gateway was draining
- plugin config implied switches existed when two plugins were not found
- Discord startup text looked like degradation to the first monitor matcher
- voice startup was mixed into the same recovery path as text reliability

Individually, each one is survivable.

Together, they produced two hours of operational fog.

The fix is not "pick a better model". A better model helps. The real fix is making the gateway honest, boring, and harder to overload.

Boring is the target. Boring means Henry can ask for work in Discord and not wonder whether his operator has silently wandered into the sea.
